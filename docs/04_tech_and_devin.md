# 04. 技術スタックとDevin運用

## 1. 技術選定（結論）

| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | **TypeScript（strict）** | 開発者の既存スキル。DevinはテキストのコードとテストでBest |
| UI | **React + Vite**（DOM中心） | ステータス・ログ・新聞などUI主体のゲーム。ミニゲームだけCanvas（PixiJSなど）を部分的に使う |
| ゲームロジック | **`packages/core`：純TS、描画やDOMへの依存ゼロ** | ヘッドレスでテスト・シミュレーションできる。Devinが自分で検証できる |
| データ | JSON ＋ **zod** スキーマ | コンテンツ追加をコード変更なしで行える。CIで検証できる |
| 乱数 | シード付きPRNG（例：mulberry32 / xoshiro128）を自前実装 | 決定論的。テストを再現できる。世界シードと同じ仕組み |
| テスト | **Vitest**（core）＋ **Playwright**（UIのスモークテスト・スクリーンショット） | Devinが「動かして画面を撮って確認する」までを自走できる |
| セーブ | **IndexedDB**（`idb`ライブラリ）＋ JSONのエクスポート／インポート | ブラウザのデータ削除に備える。クラウド同期はMVP後 |
| 配布 | **itch.io**（ブラウザゲームとして無料公開）＋ **Cloudflare Pages** | どちらも無料。Steam（$100/本）は将来の選択肢 |
| 管理 | pnpm workspaces | monorepo |

### 不採用の理由
- **Godot**：Web書き出しはCompatibilityレンダラーのみ、C#はWeb不可、Safariに問題あり。`.tscn` はDevinが扱いにくい
- **Unity**：シーンやプレハブの差分が読みにくく、AIエージェント主導の開発に不向き
- **LLMによるNPC（MVPでは不採用）**：サーバー経由のAPIは無料ゲームではコストが利用者数に比例して増え、続かない。ブラウザ内LLM（WebLLM、Chromeの組み込みPrompt API）は端末の要件が重い（Prompt APIは空き容量22GB以上、VRAM 4GB超など）。そこで**拡張点だけを用意する**：`DialogueProvider` インターフェースを置き、`TemplateProvider`（標準）と `LocalLLMProvider`（対応ブラウザでのみ有効にするオプション）を差し替えられるようにする

## 2. ディレクトリ構成

```
/
├─ AGENTS.md                 # エージェント向けルール（必読）
├─ docs/                     # 仕様（この文書群）。仕様変更は必ずここを先に更新する
├─ packages/
│  ├─ core/                  # 純ロジック（DOM禁止）
│  │  ├─ rng/                # シード付き乱数
│  │  ├─ time/               # ゲーム内時間・暦・月齢
│  │  ├─ events/             # ActionEventバス
│  │  ├─ growth/             # 経験式・定着・錆・素質
│  │  ├─ combat/             # CT制戦闘・予兆
│  │  ├─ minigame/           # MiniGame<Input,Result>の型と3エンジン（タイミング／盤面／駆け引き）
│  │  ├─ ledger/             # 作品台帳（成長・称号・新聞・年代記の元データ）
│  │  ├─ conditions/         # 条件DSLの評価器
│  │  ├─ society/            # 立場×職業・認定・人生目標
│  │  ├─ notify/             # 通知予算（S/A/B）・気配の一行
│  │  ├─ world/              # 手作りの世界＋出現抽選・噂/新聞テンプレート
│  │  ├─ chronicle/          # 年代記・伝記・継承（セーブとは別領域・別バージョン）
│  │  └─ save/               # シリアライズとバージョン移行
│  ├─ content/               # JSONデータ＋zodスキーマ（スキル、敵、称号、balance.json…）
│  └─ sim/                   # ヘッドレスのボット・バランスCIゲート（sim:growth / sim:retention）
└─ apps/
   └─ web/                   # React UI（coreを呼ぶだけ。ゲームルールを書かない）
```

### アーキテクチャ原則
1. **状態は1つの `GameState`（シリアライズ可能なプレーンオブジェクト）**。UIは読み取って描画し、`dispatch(command)` で変更を依頼する
2. `core` の公開APIは `step(state, command, rng) → { state, events }` の形を基本にする（純関数・決定論的）
3. イベントの購読者（称号・作品台帳・通知・新聞・統計）は `events` を受け取って派生状態を更新する
4. すべての数値は `balance.json` から読む
5. セーブにはスキーマのバージョンを入れ、移行関数を必ず書く。年代記は周回をまたぐので、セーブとは別の領域・別のバージョンで保存する
6. ミニゲームは固定タイムステップの状態機械にする。入力は時刻付きの列として記録し、リプレイでテストする。判定窓などの数値は `balance.json` に置く（手触りの調整はオーナーが数値で行う）

## 3. Devinの使い方

> 出典：Devin公式ドキュメント「When to use Devin」「Instructing Devin effectively」（2026-10時点で確認）。料金体系は統合後に変わっていて二次情報が食い違うため、**契約前に devin.ai/pricing で必ず確認する**こと。

### Devinが得意なこと・苦手なこと（公式の指針より）
- 得意：成功基準が明確なタスク、既存のパターンに沿う作業、テストやCIで自分で検証できるもの、**約3時間以内に終わるサイズ**、互いに独立して並列にできるタスク
- 苦手：目的が曖昧なタスク、検証手段がないもの、大きすぎる案件、**見た目の美的判断**（デザインは人間が決めて渡す）

### 運用ルール
1. **1タスク＝1機能＋テスト**。`05_roadmap.md` のタスク票をそのまま渡す
2. タスクには必ず「目的／対象ファイル／仕様の参照先（docsの節）／受け入れ基準／検証コマンド」を書く
3. 設計判断は人間（あなた）が決める。Devinには「決めて」と頼まず、選択肢がある場合は「AとBで比較して報告」と頼む
4. 繰り返しの手順（例：「新しい敵を追加する」）は **Playbook** にする。プロジェクトの規約は **Skills**（リポジトリに `SKILL.md` をコミットできる。旧Knowledgeは非推奨に移行中）と `AGENTS.md` に書く
5. UIのタスクでは「Playwrightでスクリーンショットを撮ってPRに添付」を受け入れ基準に入れる
6. 見た目は**スタイルガイド（色・フォント・余白・コンポーネント例）を人間が先に用意**して渡す
7. マージ前のチェックは `pnpm check`（lint＋型検査＋テスト＋コンテンツのスキーマ検証＋ビルド）の1コマンドに集約し、CIでも同じものを走らせる

### タスクの依頼テンプレート

```md
## タスク: [T-xx] 〈タイトル〉
### 目的
〈何のために〉
### 仕様
docs/02_growth_system.md §2〜3 に従う。
### 範囲
- 変更してよい: packages/core/growth/**
- 変更しない: apps/web/**
### 受け入れ基準
- [ ] 〈テスト可能な条件〉
- [ ] `pnpm check` が通る
### 検証方法
`pnpm --filter core test growth` と `pnpm sim:growth` / `pnpm sim:retention` の出力の要約をPRに貼る
```

## 4. アセット方針
- 基本はテキスト＋UI＋アイコン。アイコンや簡易タイルは **Kenney（CC0、商用可・クレジット不要）** から使う
- それ以外の配布元はライセンスが個別なので、`CREDITS.md` に一覧で管理する
- AI生成アセットは、使う場合に利用規約と配布先の規約（例：Steamの生成AI開示ルール）をその都度確認する
