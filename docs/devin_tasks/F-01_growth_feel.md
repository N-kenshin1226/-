## タスク: [F-01] 成長の爽快感

### 問題（実測）
- 狼との戦闘で「剣術 +3.3、回避 +4.1（未定着）」と出たのに、翌朝の起床ログは **剣術 +0.7、回避 +0.7**。原因は `balance.json` の `sleep.nightlyCapTotal: 1.7`（一晩の定着上限が全スキル合計で 1.7）。頑張った分が朝に目減りして見える
- 出自が「鍛冶屋の子」でも、全スキルが 0.0 から始まる。最初の起床ログの数字が小さく、ステータスが空っぽに見える

### やること
1. **序盤ほど大きく伸びる**ようにする。定着上限はランク（見習い・初心者…）が低いほど大きくし、上限で削られた分は「持ち越し」として起床ログに明示する（「+2.1 は明日に持ち越し」）。目安：初日に頑張れば、主なスキルが朝に +2 以上
2. **出自で初期値を持たせる**（鍛冶屋の子なら鍛冶 8〜12、など）。最初の朝から「自分の得意」が見える
3. **ランクアップを節目にする**：見習い→初心者→一人前…の到達時、起床ログで大きく扱う（後述 F-02 の演出を使う）。最初のランクアップは、普通に遊べば3日以内に起きるよう調整する
4. 行動の直後にも、得た未定着経験を数字で見せる（＋の表示が上に浮かんで消える程度）

### 受け入れ基準
- [x] 1日目に戦闘や仕事を3回以上した場合、2日目の起床ログで主なスキルが +2 以上（sim:growth「初日の伸び」: single 初朝 **+4.4**）
- [x] 出自ごとの初期値が、最初のステータス画面に出る（origins.json `initialSkills`：鍛冶屋の子は鍛冶 8〜12・目利き 3〜5・採掘 2〜4、猟師の子は観察 6〜9・釣り 4〜7・回避 2〜4。素質のばらつきと同じ `origin:<id>` 乱数源で決定論的）
- [x] 通常の遊び方で、3日以内に最初のランクアップが起きる（sim:growth「最初のランクアップ」: **3日目の朝**に 未経験→見習い）
- [x] 上限で削られた分が起床ログに「持ち越し」として出る（`WakeLine.carried` → 「《剣術》 +2.1 は明日に持ち越し」）

### 実装の判断（判断ログ）

- **持ち越しは「全量」にした**。50%消える仕様のままでは「頑張りが目減りして見える」問題が残るので、上限超過分は翌日へ100%持ち越す（`carryoverRatio` は廃止）。数日かけて必ず全部定着するので「貯金」感がある
- **定着上限のランク係数**：スキルごとの上限にはランク帯の係数（`sleep.skillRanks[].capFactor`。未経験 2.0 / 見習い 1.5 / 初心者 1.2 / 一人前 1.1 / 熟練以降 1.0）
- **合計上限は「集中した夜」だけ緩む**。全量持ち越しと合わせ、シムで検証したところ「低ランク技能を広く回す」方針に合計上限まで係数が掛かると多様型が総成長 2.8倍になり方針間の差ゲート（≤1.3）を超えた。そこで、その日の未定着の**半分以上がひとつの技能**に向かった夜（`focusShare: 0.5`）だけ、合計上限にもランク係数を掛ける形にした —— 集中して頑張った日は朝に大きく返るが、散らし回る方針の合計量は変わらない
- **ランクアップは構造化データで core から出す**（`WakeReport.rankUps` + `skillRankUp` イベント）。起床ログでは「――《剣術》は《見習い》の域に達しました。」の節目行。F-02 がこのイベントを読んで演出を足せる
- 行動直後の `+X（未定着）` 表示は既存の `gainApplied` イベントが担っていたため、CLI の定型文に「（未定着）」を明示するだけに留めた（web の行生成 `eventLines` は既に対応済み）
- web のステータス階級（vocab.ts）は §1 のランク表と一致していなかったので、境界を 0/10/25/40/60/80/95/100 に揃えた（「未経験」と「???」の帯を追加）

### 測定結果（sim:growth）

| 指標 | 変更前 | 変更後 |
|---|---|---|
| 初日の主スキル（single） | ―（+1.0 程度） | **+4.4** |
| 最初のランクアップ | ― | **3日目の朝** |
| 方針間の差 | 1.16倍 | 1.21倍（≤1.3 を維持） |
| 主スキル@3h（single） | 25〜40帯内 | 39.9 |

### 共通
- 背景：オーナーが実際に遊んだ感想は **「刺激があんまりない」**。このタスクの目的は、それを直すこと。仕様の細部より「遊んで気持ちいいか」を優先してよい（変えた点は判断ログに書く）
- `docs/design/` の見た目のルールを守る。演出の数値（時間・大きさ・音量など）は theme.ts か balance.json に置き、オーナーが調整できるようにする
- バランスCIゲート（`pnpm sim:*`）が落ちる場合は、閾値ではなく数値で合わせる。仕様の意図とぶつかる場合は判断ログに「要確認」
- PRに、変更前と変更後のスクリーンショット（動きがあるものは数枚の連続画像）を添付する
